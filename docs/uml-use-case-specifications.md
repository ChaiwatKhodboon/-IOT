# คำอธิบาย Use Case รายตัว — ระบบยืม–คืนอุปกรณ์ IoT

เอกสารสำหรับคัดลอกลงรายงาน ใช้รหัสและชื่อเดียวกับ Use Case Diagram ใน `uml-system.md` ยึดรูปแบบบทที่ 8: **Use Case Title, Use Case ID, Primary Actor, Stakeholder Actor, Trigger, Preconditions, Main Flow, Exceptional Flow, Postconditions** คำว่า User หมายถึงบทบาท `user`; Admin หมายถึงบทบาท `admin`; “สมาชิก” หมายถึงบัญชีที่เข้าสู่ระบบซึ่งเป็นได้ทั้งสองบทบาท ลำดับขั้นใน Main Flow เป็นเหตุการณ์ทางธุรกิจ ส่วน API/ฐานข้อมูลอยู่ในเอกสาร UML หลัก

## UC01 สมัครสมาชิก

| หัวข้อ | รายละเอียด |
|---|---|
| Use Case ID / Title | UC01 / สมัครสมาชิก |
| Primary Actor | ผู้เยี่ยมชม |
| Stakeholder Actor | ไม่มี |
| Trigger | ผู้เยี่ยมชมเลือกสมัครสมาชิกและส่งแบบฟอร์ม |
| Preconditions | ยังไม่ต้องเข้าสู่ระบบ; ผู้เยี่ยมชมมีข้อมูลที่ใช้สมัคร |
| Main Flow | 1. ผู้เยี่ยมชมกรอกชื่อบัญชี อีเมล รหัสผ่าน ชื่อ และรหัสนิสิตถ้ามี<br>2. ระบบตรวจรูปแบบ ชื่อบัญชี และอีเมล<br>3. ระบบเข้ารหัสรหัสผ่านและสร้างบัญชีบทบาท User<br>4. ระบบแจ้งสมัครสำเร็จและให้เข้าสู่ระบบ |
| Exceptional Flow | E1: ชื่อบัญชีสั้นกว่า 4 ตัว อีเมลไม่ถูกต้อง หรือรหัสผ่านสั้นกว่า 8 ตัว → แจ้งแก้ไขแบบฟอร์มและไม่สร้างบัญชี<br>E2: ชื่อบัญชีหรืออีเมลซ้ำ → แจ้งว่าถูกใช้แล้วและไม่สร้างบัญชี<br>E3: บันทึกข้อมูลไม่สำเร็จ → แจ้งข้อผิดพลาดและคงสถานะก่อนสมัคร |
| Postconditions | มีแถว `users` ใหม่ที่ `role=user`; ยังไม่ได้เข้าสู่ระบบอัตโนมัติจากการสมัคร |

## UC02 เข้าสู่ระบบด้วยรหัสผ่าน

| หัวข้อ | รายละเอียด |
|---|---|
| Use Case ID / Title | UC02 / เข้าสู่ระบบด้วยรหัสผ่าน |
| Primary Actor | ผู้เยี่ยมชม |
| Stakeholder Actor | ไม่มี |
| Trigger | ผู้เยี่ยมชมกดเข้าสู่ระบบ |
| Preconditions | มีบัญชีที่ใช้งานได้ |
| Main Flow | 1. ผู้เยี่ยมชมกรอกข้อมูลบัญชีและรหัสผ่าน<br>2. ระบบค้นหาบัญชีที่เปิดใช้งานและตรวจรหัสผ่าน<br>3. ระบบสร้าง JWT และส่งข้อมูลบัญชีกับบทบาทให้ไคลเอนต์<br>4. ไคลเอนต์แสดงหน้าหลักและเมนูตามบทบาท |
| Exceptional Flow | E1: ไม่พบบัญชี บัญชีใช้ไม่ได้ หรือรหัสผ่านผิด → แจ้งว่าข้อมูลเข้าสู่ระบบไม่ถูกต้อง ไม่ออก JWT<br>E2: session เดิมหมดอายุเมื่อเรียก API → ส่งกลับหน้าเข้าสู่ระบบเพื่อยืนยันตัวตนใหม่ |
| Postconditions | ไคลเอนต์มี session สำหรับเรียก API จนหมดอายุหรือออกจากระบบ |

## UC03 เข้าสู่ระบบด้วย Google

| หัวข้อ | รายละเอียด |
|---|---|
| Use Case ID / Title | UC03 / เข้าสู่ระบบด้วย Google |
| Primary Actor | ผู้เยี่ยมชม |
| Stakeholder Actor | Google Identity |
| Trigger | ผู้เยี่ยมชมเลือกปุ่ม Google |
| Preconditions | ตั้งค่า Google client ในระบบและเข้าถึงบริการ Google ได้ |
| Main Flow | 1. ระบบสร้าง challenge สำหรับการเข้าสู่ระบบครั้งนี้<br>2. ผู้เยี่ยมชมเลือกบัญชี Google และส่ง credential กลับ<br>3. ระบบตรวจลายเซ็น แหล่งออก token ผู้รับ token วันหมดอายุ nonce และอีเมลที่ยืนยันแล้ว<br>4. ระบบค้นหาบัญชีที่ผูก Google; ถ้าไม่พบและมีสิทธิ์สร้างใหม่ ระบบสร้างบัญชี User<br>5. ระบบออก JWT และแสดงหน้าหลัก |
| Exceptional Flow | E1: credential หรือ challenge ไม่ผ่าน → แจ้งเข้าสู่ระบบไม่สำเร็จ ไม่ออก JWT<br>E2: พบอีเมลบัญชีเดิมที่ยังไม่ผูก → ดำเนิน UC22<br>E3: บัญชีปิดใช้งานหรือผูกกับ Google อื่น → แจ้งข้อผิดพลาด<br>E4: ไม่เข้าเงื่อนไขการสร้างบัญชีอัตโนมัติ → แจ้งให้สมัครด้วยอีเมล/รหัสผ่านก่อน |
| Postconditions | มี session ของบัญชีที่ผูก Google; หากสร้างใหม่ `role=user` |

## UC04 รีเซ็ตรหัสผ่านด้วย OTP

| หัวข้อ | รายละเอียด |
|---|---|
| Use Case ID / Title | UC04 / รีเซ็ตรหัสผ่านด้วย OTP |
| Primary Actor | ผู้เยี่ยมชม |
| Stakeholder Actor | บริการอีเมล |
| Trigger | ผู้เยี่ยมชมเลือก “ลืมรหัสผ่าน” |
| Preconditions | ผู้ใช้ควบคุมอีเมลของบัญชีที่เปิดใช้งาน; บริการอีเมลพร้อมใช้งาน |
| Main Flow | 1. ผู้เยี่ยมชมกรอกอีเมล<br>2. ระบบสร้าง OTP หกหลักและส่งไปยังอีเมล<br>3. ผู้เยี่ยมชมกรอก OTP และรหัสผ่านใหม่<br>4. ระบบตรวจรหัส อายุ และจำนวนครั้งที่ลอง<br>5. ระบบบันทึกรหัสผ่านใหม่และทำเครื่องหมาย OTP ว่าใช้แล้ว<br>6. ระบบแจ้งให้เข้าสู่ระบบด้วยรหัสใหม่ |
| Exceptional Flow | E1: อีเมลไม่ถูกต้อง → แจ้งแก้ไข<br>E2: ไม่พบบัญชี → ตอบข้อความทั่วไปโดยไม่เปิดเผยว่ามีบัญชีหรือไม่<br>E3: ขอ OTP ถี่เกินเกณฑ์ → ไม่ส่งรหัสใหม่<br>E4: ส่งอีเมลล้มเหลว → แจ้งให้ลองใหม่<br>E5: OTP ผิด หมดอายุ ใช้แล้ว หรือผิดครบจำนวนที่กำหนด → ไม่เปลี่ยนรหัสผ่าน |
| Postconditions | เมื่อสำเร็จรหัสผ่านใหม่มีผล; OTP ที่ใช้แล้วใช้ซ้ำไม่ได้ |

## UC05 จัดการโปรไฟล์

| หัวข้อ | รายละเอียด |
|---|---|
| Use Case ID / Title | UC05 / จัดการโปรไฟล์ |
| Primary Actor | สมาชิก |
| Stakeholder Actor | ไม่มี |
| Trigger | สมาชิกเปิดหน้าโปรไฟล์และส่งข้อมูลที่แก้ไข |
| Preconditions | เข้าสู่ระบบแล้ว |
| Main Flow | 1. ระบบแสดงข้อมูลบัญชีปัจจุบัน<br>2. สมาชิกแก้ชื่อบัญชี ชื่อ อีเมล หรือข้อมูลโปรไฟล์ที่หน้าเว็บรองรับ และอาจเลือกรูปใหม่<br>3. ระบบตรวจรูปแบบและสิทธิ์ของบัญชีตนเอง<br>4. ระบบบันทึกและแสดงข้อมูลล่าสุด |
| Exceptional Flow | E1: ชื่อบัญชีหรืออีเมลซ้ำ → แจ้งแก้ไข ไม่บันทึกค่าที่ผิด<br>E2: ชื่อบัญชีไม่ตรงรูปแบบ → แจ้งรูปแบบที่ใช้ได้<br>E3: รูปไม่ใช่ JPG/PNG/WebP หรือใหญ่กว่า 2 MB → ปฏิเสธรูปนั้น<br>E4: session ไม่ถูกต้อง → ให้เข้าสู่ระบบใหม่ |
| Postconditions | `users` ของสมาชิกมีข้อมูลโปรไฟล์ล่าสุด; การเปลี่ยนที่ถูกบันทึกในฐานข้อมูลเข้า Audit ตาม trigger |

## UC06 ค้นหาและดูอุปกรณ์

| Primary Actor | สมาชิก |
| Stakeholder Actor | ไม่มี |

## UC07 ยืมอุปกรณ์

| หัวข้อ | รายละเอียด |
|---|---|
| Use Case ID / Title | UC07 / ยืมอุปกรณ์ |
| Primary Actor | สมาชิก |
| Stakeholder Actor | ผู้ดูแลคลัง ซึ่งต้องติดตามของที่ถูกยืม |
| Trigger | สมาชิกกดยืนยันการยืม |
| Preconditions | เข้าสู่ระบบ; อุปกรณ์ไม่ retired และมีจำนวนพร้อมยืมเพียงพอ |
| Main Flow | 1. สมาชิกเลือกอุปกรณ์และกรอกจำนวน ชื่อผู้ยืม กำหนดคืน และหมายเหตุที่ต้องการ<br>2. ระบบตรวจข้อมูลและยอดพร้อมยืมล่าสุดภายใต้การล็อกข้อมูล<br>3. ระบบลดจำนวนพร้อมยืมและสร้างรายการ borrowed ของสมาชิก<br>4. ระบบบันทึกประวัติการเปลี่ยนแปลงและยืนยันยืมสำเร็จ |
| Exceptional Flow | E1: อุปกรณ์หรือจำนวนไม่ถูกต้อง → แจ้งแก้ไข ไม่สร้างรายการ<br>E2: อุปกรณ์ retired หรือไม่มีพร้อมยืม → แจ้งว่าไม่มีอุปกรณ์ที่ยืมได้<br>E3: อีกคนยืมก่อนจนเหลือไม่พอ → แจ้งจำนวนที่เหลือและย้อนรายการนี้<br>E4: ฐานข้อมูลหรือ Audit ไม่สำเร็จ → rollback ทั้งจำนวนและรายการยืม |
| Postconditions | `loans.status=borrowed`; `equipment.available_quantity` ลดลงเท่าจำนวนยืม; ไม่มีขั้น Admin อนุมัติ |

## UC08 ส่งคำขอคืน

| หัวข้อ | รายละเอียด |
|---|---|
| Use Case ID / Title | UC08 / ส่งคำขอคืน |
| Primary Actor | User ผู้เป็นเจ้าของรายการยืม |
| Stakeholder Actor | Admin ผู้จะตรวจรับของจริง |
| Trigger | User กดส่งคำขอคืน |
| Preconditions | เข้าสู่ระบบ; รายการของตนยัง borrowed; ไม่มีคำขอคืนที่รอตรวจรับ |
| Main Flow | 1. User เลือกรายการและกรอกจำนวนแยก normal, damaged, lost, abnormal พร้อมหมายเหตุ<br>2. ระบบตรวจผลรวมว่าอยู่ระหว่าง 1 ถึงจำนวนค้างและตรวจเจ้าของรายการ<br>3. ระบบบันทึกคำขอใน `pending_return` พร้อมผู้แจ้งและเวลา<br>4. ระบบแจ้งสถานะรอตรวจรับให้ User |
| Exceptional Flow | E1: จำนวนผิดรูปแบบ รวมเป็นศูนย์ หรือเกินค้าง → แจ้งแก้ไข ไม่สร้างคำขอ<br>E2: ไม่ใช่เจ้าของหรือรายการไม่ borrowed → แจ้งไม่พบรายการที่คืนได้<br>E3: มีคำขอค้าง → แจ้งว่ารอตรวจรับอยู่แล้ว<br>E4: ส่ง `requestId` เดิมด้วยเนื้อหาเดิม → คืนผลเดิม; หากเนื้อหา/ผู้แจ้ง/รายการต่างกัน → ปฏิเสธ |
| Postconditions | มี `pending_return` แต่ `loans.status` ยัง borrowed; ยอดค้างและสต็อกไม่เปลี่ยน |

## UC09 ดูประวัติและติดตามรายการ

| หัวข้อ | รายละเอียด |
|---|---|
| Use Case ID / Title | UC09 / ดูประวัติและติดตามรายการ |
| Primary Actor | สมาชิก |
| Stakeholder Actor | ไม่มี |
| Trigger | สมาชิกเปิดหน้าประวัติหรือติดตาม |
| Preconditions | เข้าสู่ระบบแล้ว |
| Main Flow | 1. สมาชิกเปิดรายการยืม–คืน<br>2. ระบบอ่านรายการพร้อมอุปกรณ์ ผู้ยืม ยอดค้าง ส่วนคืน กำหนดคืน และสภาพคืน<br>3. สมาชิกค้นหา กรอง หรือเรียงรายการ<br>4. ระบบแสดงสถานะรอตรวจรับ เหตุผลที่ถูกส่งกลับ และรายการเกินกำหนดตามข้อมูลปัจจุบัน |

| Main Flow | 1. ระบบแจ้งว่าต้องเชื่อมบัญชีเดิม<br>2. เจ้าของบัญชีกรอกรหัสผ่านของระบบ<br>3. ระบบตรวจรหัสผ่านกับบัญชีเดิม<br>4. ระบบบันทึก Google subject ให้บัญชีเดิม<br>5. ระบบออก session และเข้าสู่ระบบ |
| Exceptional Flow | E1: รหัสผ่านเดิมผิด → ปฏิเสธการเชื่อมและไม่ออก session<br>E2: บัญชีถูกปิดใช้งาน → ปฏิเสธ<br>E3: บัญชีผูก Google อื่นอยู่แล้ว → แจ้งความขัดแย้ง<br>E4: credential Google ไม่ผ่าน → กลับไปข้อผิดพลาดของ UC03 |
| Postconditions | บัญชีเดิมเชื่อม Google และใช้เข้าสู่ระบบครั้งต่อไปได้; ไม่สร้างบัญชีซ้ำ |

ข้อสังเกตสำหรับอาจารย์: สไลด์บทที่ 8 เรียกเส้นความสัมพันธ์ `<<uses>>` ในตัวอย่างบางหน้า ในเอกสารนี้ใช้ศัพท์ UML ที่พบทั่วไปว่า `<<include>>` และ `<<extend>>` โดยการเชื่อม Google เดิมเป็นทางเลือกที่เกิดเฉพาะเมื่อพบบัญชีเดิม จึงใช้ `<<extend>>` ส่วนขั้นตรวจตัวตนที่เป็นเงื่อนไขก่อนทำ Use Case ไม่ได้วาดเป็น `<<include>>` ซ้ำกับทุกวงรี
